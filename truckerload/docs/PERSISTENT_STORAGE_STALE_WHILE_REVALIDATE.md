# Offline-first / Local-first: локальное хранилище и Stale-While-Revalidate

## Описание требований

Реализована стратегия **Offline-first**: данные загружаются **мгновенно из Room**, не дожидаясь ответа от Telegram/сервера. Синхронизация с ботом выполняется в фоне.

### Основные требования

- **Логика загрузки:** При открытии экрана сначала проверь наличие данных в локальном хранилище (Room / SQLite). Если данные есть — сразу отобрази их.
- **Фоновое обновление:** Параллельно с отображением локальных данных отправь запрос к API (или запусти синхронизацию). Когда придут свежие данные — обнови интерфейс и сохрани новую версию в локальную БД.
- **Обработка ошибок:** Если интернета нет, приложение продолжает работать на старых данных без бесконечных индикаторов загрузки.
- **Инструментарий:** Room (SQLite), Kotlin Flow, ViewModel, при необходимости — WorkManager для фоновой синхронизации.

Код должен быть чистым, с комментариями, где именно происходит **сохранение** и **чтение**.

## Как это работает (схема)

Паттерн называется **«Stale-While-Revalidate»** (показываем старое, пока проверяем новое).

| Шаг | Действие |
|-----|----------|
| 1. Запуск | Приложение запрашивает данные у **Local DB (Room)**. |
| 2. Мгновенный UI | Пользователь сразу видит список (лоуды, зарплаты, дизель) из кэша. |
| 3. Запрос | Приложение тихо делает запрос к серверу (Telegram API, REST и т.д.). |
| 4. Синхронизация | Новые данные записываются в Room поверх старых. |
| 5. Обновление | Экран плавно обновляется за счёт подписки на Flow. |

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│   UI        │────▶│  ViewModel   │────▶│  Repository │
│ (Compose)   │◀────│  (StateFlow) │◀────│  (Flow from │
└─────────────┘     └──────────────┘     │   Room DAO) │
       │                    │            └──────┬──────┘
       │                    │                   │
       │                    │            ┌──────▼──────┐
       │                    │            │  Room DB    │  ◀── чтение при открытии
       │                    │            │  (SQLite)   │  ◀── запись при синке
       │                    │            └──────┬──────┘
       │                    │                   │
       │                    │            ┌──────▼──────┐
       │                    └───────────│ SyncWorker  │  ◀── фоновый fetch, пишет в Room
       │                                 │ (Telegram)  │
       │                                 └─────────────┘
```

## Где в проекте происходит чтение и запись

### Чтение (мгновенный показ из памяти)

- **Repository** — метод вида `getAllLoads(): Flow<List<Load>>` читает из **Room DAO** (`loadDao.getAllLoads()`). Данные приходят из SQLite.
- **ViewModel** — подписывается на этот Flow через `stateIn` / `collect` и обновляет `UiState`. При первом открытии экрана UI сразу получает то, что уже есть в БД (в т.ч. пустой список).
- **Экран (Compose)** — отображает `uiState.loads` без ожидания сети.

Файлы: `LoadRepository.kt` (getAllLoads), `HomeViewModel.kt` (подписка на loadsFromDb), `PaycheckRepository` / `DieselRepository` — аналогично.

### Запись (сохранение в локальную память)

- **Repository** — методы `insertLoad`, `updateLoad`, `insertPaycheck`, `insertDiesel` и т.д. пишут в Room (DAO.insert/update). Это и есть «сохранение в локальную память».
- **Sync** — `TelegramSyncWorker` после получения данных из Telegram API вызывает `loadRepository.insertLoad(...)`, `paycheckRepository.insertPaycheck(...)` и т.д. Таким образом новая версия данных попадает в Room, Flow в ViewModel автоматически эмитит обновлённый список, и UI обновляется.

Файлы: `LoadRepository.kt` (insert/update), `TelegramSyncWorker.kt` (вызовы insert после парсинга).

### Обработка ошибок (нет интернета)

- UI **никогда не зависит от сети** для первичного отображения: данные только из Room.
- Синхронизация (Worker или вызов API) при ошибке сети может завершиться с `Result.failure()`; приложение при этом продолжает показывать старые данные из БД, без бесконечного загрузчика.

## Краткий чеклист по стеку

| Задача | Технология в проекте |
|--------|----------------------|
| Локальное хранилище | **Room** (SQLite) |
| Реактивное чтение | **Kotlin Flow** из DAO → Repository → ViewModel |
| UI состояние | **StateFlow** в ViewModel, подписка в Compose |
| Фоновое обновление | **WorkManager** (TelegramSyncWorker) или корутины в ViewModel |
| Отображение без ожидания сети | Данные всегда берутся из Room; sync только дописывает в БД |

## Реализованные улучшения (Offline-first)

| Компонент | Реализация |
|-----------|------------|
| **Initial Load** | UI читает из Room через Flow — данные показываются сразу при открытии экрана |
| **Background Sync** | TelegramSyncWorker: при старте приложения и при возврате (ProcessLifecycleOwner.onStart) |
| **Optimistic Updates** | AddLoadScreen: парсинг + сохранение в Room → UI обновляется через Flow без ожидания бота |
| **Sync частота** | Worker перезапускается каждую 1 мин в фоне; при каждом onStart — немедленный запуск |
